# 🧭 6단계 노드 파이프라인 가이드 & 안티패턴 분석서 (ARCHITECTURE_PIPELINE_GUIDE.md)

이 문서는 개발자와 AI 에이전트가 시스템 아키텍처를 설계하고 계획서(`implementation_plan.md`)를 작성할 때, **기능 단위의 올바른 6단계 파이프라인 흐름을 이해하고 과거의 전형적인 오해/안티패턴을 방지**하기 위해 작성되었습니다.

---

## 1. 과거의 오해와 구조적 원인 분석 (Post-Mortem)

### 🚨 전형적인 오해 사례 (Anti-Pattern)
과거 AI 에이전트들은 계획서(`implementation_plan.md`) 작성 시 다음과 같은 심각한 오류를 범하곤 했습니다:
1. **파일 카탈로그식 테이블 작성**: 파이프라인 표의 행(Row)을 파일 단위로 잡고, 연산/판단/출력 파일마다 기계적으로 `트리거(@trigger)`와 `저장소(@store)` 열을 제각각 채워 넣음.
2. **거대 기능 뭉뚱그리기 (Feature Fat-clustering)**: 'AI 연동'이나 '기획서 작업'처럼 거시적인 목적을 하나의 `@feature`로 묶어서, 사용자의 시작 버튼도 다르고 저장 대상도 전혀 다른 복수의 독립 작업을 한 표에 뒤섞음.
3. **인과 흐름의 실종**: "어디서 시작해서(입력) 어떤 가드를 거쳐(판단) 어떤 데이터로 변환되어(연산) 어디에 저장되고(저장소) 화면 어디에 그려지는가(출력)"라는 시간적/논리적 인과 체인이 완전히 끊어짐.

### 🔍 왜 이런 오해가 발생했는가?
1. **문서 서술의 유도 오류**:
   - 기존 가이드라인에 `필수 포함 열: 파일 경로, 단계(@phase), 대상(@target), 작동 트리거(@trigger), 저장소(@store)...`라고 나열되어 있어, 에이전트가 이를 "파일 하나당 행 하나를 할당하는 속성 카탈로그"로 오인함.
2. **기능(@feature) 분할 기준(Granularity)의 모호함**:
   - "사용자가 체감하는 개별 단위 기능"이라는 설명만으로는, '프롬프트 복사'와 '문서 임포트'를 분리해야 하는지 하나로 묶어야 하는지 판별하지 못함.
3. **인스펙터 보드(`dev-admin`) 시각화 구조와의 정렬 부족**:
   - `dev-admin` 대시보드는 각 Feature 안에서 `입력 ⚡(1) ➡️ 판단 ⚖️(2) ➡️ 연산 ⚙️(3) ➡️ API 🌐(4) ➡️ 저장소 💾(5) ➡️ 출력 🎨(6)` 순으로 체인(`script-chain`)을 엮고 있었으나, 계획서 작성 템플릿에는 이 순서열 흐름이 직관적으로 드러나지 않았음.

## 2. 올바른 아키텍처 멘탈 모델

### 💡 1개 기능(`@feature`)의 절대 정의
> **"1개의 기능(@feature)이란, 사용자의 1개 시작점(Trigger)에서 출발하여 1개의 최종 결과(Render)로 도달하는 하나의 완결된 라이프사이클 체인이다."**

- 사용자가 누르는 버튼이 다르거나 시작 조건이 다르면 ➡️ **서로 다른 별개의 `@feature`**입니다.
- 도달하는 최종 저장소나 목적지가 다르면 ➡️ **서로 다른 별개의 `@feature`**입니다.
- **예시**:
  - `[AI 양식 프롬프트 클립보드 복사]`: 헤더 버튼 클릭 ➡️ 클립보드 저장 ➡️ 토스트 렌더링 (Feature A)
  - `[외부 AI 기획 텍스트 문서 임포트]`: 모달 붙여넣기 ➡️ DocNode 변환 ➡️ 로컬 파일 저장 ➡️ 아코디언 렌더링 (Feature B)
  - `[단락 본문 내 인라인 HTML 샌드박스]`: 툴바 삽입 클릭 ➡️ 마크다운 세그먼트 분할 ➡️ 파일 저장 ➡️ 혼합 본문 렌더링 (Feature C)

## 3. 6단계 노드 파이프라인의 인과적 순서열

모든 기능은 반드시 아래 6단계 중 필요한 노드들을 순서대로 통과하는 **단방향 파이프라인 체인**으로 표현되어야 합니다:

```text
[⚡ 1. 입력 (Trigger)]
        ⬇️
[⚖️ 2. 판단 (Decision)]
        ⬇️
[⚙️ 3. 연산 (Compute)]
        ⬇️
[🌐 4. API (Network)]  (선택: 외부 통신이 있는 경우)
        ⬇️
[💾 5. 저장소 (Store)]
        ⬇️
[🎨 6. 출력 (Render)]
```

### 단계별 명확한 정의
1. **⚡ 입력 (Trigger)**: 파이프라인의 시작점. 사용자의 클릭, 타이핑, 모달 오픈, URL 진입, 타이머 등.
2. **⚖️ 판단 (Decision)**: 가드 및 검증. 권한 검사, 유효성 검증(Validation), 포맷 일치 여부, 조건 분기.
3. **⚙️ 연산 (Compute)**: 데이터 변환 및 계산. 순수 가공 함수, 파싱, 정규화, 수학적 연산.
4. **🌐 API (Network)**: 네트워크 통신. 백엔드 통신, 외부 API 호출, 웹소켓 연동 (네트워크가 없는 순수 프론트엔드 작업의 경우 생략 가능).
5. **💾 저장소 (Store)**: 영속성 및 상태 반영. LocalStorage, FileSystem, Zustand/Redux 전역 상태, IndexedDB 쓰기/읽기.
6. **🎨 출력 (Render)**: 사용자 감각 피드백. JSX UI 렌더링, 스타일 반영, 토스트 메시지, 사운드.

## 4. 계획서(`implementation_plan.md`) 작성 표준 템플릿

계획서를 작성할 때는 하나의 기능마다 아래와 같이 **단계(Phase)를 행(Row)으로 두고 위에서 아래로 흐르는 순서열**로 작성해야 합니다:

### 템플릿 형식
```markdown
### [도메인: <도메인명>] ➡️ [기능: <독립 기능명>]
> **목적**: <이 기능이 해결하는 사용자 인터랙션과 완결된 목표 1줄 요약>

```text
[⚡ 입력 (Trigger)] ──> [⚖️ 판단 (Decision)] ──> [⚙️ 연산 (Compute)] ──> [💾 저장소 (Store)] ──> [🎨 출력 (Render)]
```

| 순서 | 단계 (@phase) | 담당 파일 (구현체) | 요소 본질 (@target) | 세부 역할 및 흐름 설명 |
| :---: | :--- | :--- | :--- | :--- |
| **1** | **⚡ 입력 (Trigger)** | `경로/파일명` | <버튼/인풋 등 트리거 요소> | <어떤 사용자 행동으로 이 체인이 시작되는가> |
| **2** | **⚖️ 판단 (Decision)** | `경로/파일명` | <검증기/가드 요소> | <어떤 조건과 유효성을 검사하여 분기하는가> |
| **3** | **⚙️ 연산 (Compute)** | `경로/파일명` | <변환/계산 로직 요소> | <어떤 계산/데이터 가공/파싱이 일어나는가> |
| **4** | **🌐 API (Network)** | `경로/파일명` | <네트워크 클라이언트> | <외부 통신 규격 (없을 경우 생략)> |
| **5** | **💾 저장소 (Store)** | `경로/파일명` | <대상 저장소> | <어떤 저장소(FileSystem, LocalStorage 등)에 저장되는가> |
| **6** | **🎨 출력 (Render)** | `경로/파일명` | <렌더링 컴포넌트/토스트> | <최종적으로 사용자 화면에 무엇이 어떻게 그려지는가> |
```

## 5. 안티패턴 vs 모범 사례 비교

### ❌ 잘못된 작성 방식 (안티패턴: 파일 속성 나열)
```markdown
<!-- 나쁜 예: 파일마다 트리거와 저장소를 억지로 채워 흐름이 보이지 않음 -->
| 파일 경로 | 단계 | 대상 | 작동 트리거 | 저장소 |
| lib/parser.ts | 연산 | 파서 | 텍스트 입력 | - |
| modal/ImportModal.tsx | 입력 | 모달 | 버튼 클릭 | LocalStorage |
| doc/Section.tsx | 출력 | 섹션 | 렌더링 | - |
```

###  올바른 작성 방식 (모범 사례: 단일 체인 순서열)
```markdown
<!-- 좋은 예: Trigger에서 Render까지 1개의 기능이 완성되는 인과 체인 -->
| 순서 | 단계 (@phase) | 담당 파일 | 요소 본질 (@target) | 세부 역할 및 흐름 설명 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | ⚡ 입력 (Trigger) | `modal/ImportModal.tsx` | [가져오기] 버튼 | 사용자가 AI 텍스트를 붙여넣고 버튼 클릭 |
| 2 | ⚖️ 판단 (Decision) | `lib/parser.ts` | 텍스트 유효성 검사기 | JSON 포맷 및 필수 제목 필드 누락 여부 판별 |
| 3 | ⚙️ 연산 (Compute) | `lib/parser.ts` | DocNode 트리 변환기 | 마크다운 코드블록 제거 및 데이터 트리 구조 가공 |
| 4 | 💾 저장소 (Store) | `pages/WorkspaceView.tsx` | 파일 시스템 & 상태 | 생성된 단락들을 로컬 content.md, node.json에 저장 |
| 5 | 🎨 출력 (Render) | `doc/Section.tsx` | 아코디언 본문 뷰어 | 메인 화면에 새 단락들을 펼쳐 렌더링하고 완료 알림 표시 |
```

## 6. 개발자 & 에이전트 체크리스트
- [ ] 하나의 기능(@feature) 표 안에 서로 다른 버튼 클릭이나 서로 다른 저장 인터랙션이 섞여 있지 않은가?
- [ ] 파이프라인 표가 파일 나열이 아닌, `입력 ➡️ 판단 ➡️ 연산 ➡️ (API) ➡️ 저장소 ➡️ 출력`의 순서열로 작성되었는가?
- [ ] 각 소스 파일 상단의 JSDoc 주석(`@domain`, `@feature`, `@phase`, `@target`, `@desc`)이 이 파이프라인과 1:1로 일치하는가?
- [ ] `npm run lint` 및 `npm run test:run` 실행 시 아키텍처 주석 및 단위 로직이 100% 무결성을 유지하는가?
